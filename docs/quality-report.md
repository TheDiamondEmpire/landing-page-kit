# Landing Page Kit: quality report

> **Where the code is.** The measurement scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

Version 0.1.0 by The Diamond Empire. This report states what was measured, how, what the numbers were, and what the checks cannot tell you. Every number in the results table is generated by `npm run report:table` from files in [results/](../results/); none is typed by hand. Timing and performance scores are deliberately not measured: the machine that built this is shared and loaded, and timings from it would not mean anything.

## Verdicts

These sentences interpret the table above; the table is the source of truth.

- **Validity:** all pages are valid under the recommended `html-validate` preset. This is the validator's rule set, not the W3C Nu validator.
- **axe-core:** zero violations in every variant that was run. "Needs review" items are things axe could not decide by itself: on the pricing page the tick glyphs in the comparison table (only non-text characters) and, at 320 px wide, table cells partly scrolled out of view; on the app page, at 320 px wide only, the captions of the screenshots that sit outside the visible part of the horizontal gallery. Those items were not reviewed by a person for this report, so they are open.
- **Contrast from tokens:** every checked pair passes in both themes. This covers token pairs, not every pixel; axe checks the rendered colours as well.
- **Weight and requests:** every page is within the budgets that were set before the pages were written. The measured values are in the table. The art is SVG, so there are no raster images.
- **Third parties:** zero requests to any other origin in the browser, and no URL to another host in any shipped file.
- **Forms:** validation messages, one adapter call, no network request and double-submit protection pass on all eight pages, over http and from the extracted ZIP over file://.
- **ZIP:** deterministic (identical bytes on two builds) and the extracted pages load with no console error and no failed request.

## Limits and threats to validity

- **Automated accessibility testing finds only part of the problems that affect people.** axe-core, contrast ratios and keyboard scripts cannot judge whether alternative text is meaningful, whether the reading order makes sense, whether link text is clear, whether the wording is easy to understand, or how a page works with a screen reader, a magnifier, speech input or switch devices. No screen reader was used for this report. Nothing here is a statement of conformance with the Web Content Accessibility Guidelines at any level.
- **One browser engine.** The browser checks ran in one version of Chrome on Windows (headless, one viewport emulation at a time). Firefox, Safari and real phones were not tested. Layout differences there are possible.
- **Viewport widths 320, 768 and 1280 only.** Other widths, zoom to 200 percent and text-spacing overrides were not tested. Horizontal overflow was tested only at those three widths.
- **Contrast.** The contrast script checks a fixed list of token pairs. A new component with a new colour combination is not covered until its pair is added to the list.
- **axe results depend on page state.** The scans ran on the loaded page, with the form in its error state and with the mobile menu open. Open FAQ items, hover states and the pricing switch in its yearly position were not scanned separately.
- **Sample content.** The pages contain invented sample names, prices and quotes. The measurements describe the templates, not any customer's final pages.
- **Open Graph** is checked only for presence and shape: no social network preview was fetched.
- **File-system loading** was tested in Chrome. `<script type="module">` is blocked from file:// pages in that Chrome (recorded in `results/package.json`), which is why the kit's scripts are classic scripts.
- **Not measured:** load time, rendering performance, Lighthouse scores, real-user behaviour, conversion, search ranking. No claim about any of these is made.
- **The GitHub Actions workflow was never run.** It was written to run the same commands as local development, but this was built and verified locally only.
- **Shared machine.** Other jobs were running during the work. This does not affect byte counts or pass/fail checks, which are deterministic, and is the reason no timings are reported.

## Change log

Disclosure of reruns and changes made after something was measured. Dates are the build date in the metadata.

1. **Budgets first.** `tests/budgets.json` was written before any page existed. Its values have not changed.
2. **First exploratory measurement.** While building, the checks were run repeatedly on the development folder. The first full weight measurement found the pricing page's JavaScript at 14,524 bytes against the 14,000-byte budget. The budget was kept; the long provider examples in `js/submit-adapter.js` comments were reduced to one example (the others moved to `docs/guide/04-connect-a-form.md`). That is a post-hoc code change made because a budget failed.
3. **Exploratory axe runs** found three real problems that were fixed in the CSS: a horizontal scroll at 320 px on the pricing page (visually hidden text inside a scrolling table was positioned against the page), "needs review" items on the numbered steps (an absolutely positioned counter), and a dark-theme contrast error on the event page hero (a hard-coded pink hero background). The last was found by the token contrast script.
4. **A measurement artifact was fixed in the test, not the page.** The first axe run on the forced dark theme reported contrast violations on buttons on one page. The cause was axe sampling the colours while the buttons were still in their 150 ms colour transition after the theme attribute was set. The test now waits 500 ms after switching. All other pages passed without the wait.
5. **A test bug was fixed.** The "no network request on submit" check counted the browser's late favicon request. The check now starts counting after the page is idle and the first validation steps are done.
6. **html-validate** first reported the doctype style and two `role="region"` uses on a `div`. The markup was changed (`<!DOCTYPE html>`, `<section>`); no rule was disabled.
7. **Authoring.** The eight pages were first written with a throwaway script outside the repository and then maintained as plain HTML; the HTML files are the source of truth.
8. **Milestone order.** M1 to M4 were built in order with the contrast script, `html-validate` and a visual check after each page. The full browser test suite (M5) was assembled after all pages existed and then applied to every page; it was not run milestone by milestone.
9. **Final run.** The measurement set and the test suite were run from a clean copy at a short path after the code was frozen; the outputs were written outside that copy and then copied into `results/`.
